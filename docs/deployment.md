# 定制实例部署指南

本文件可公开，只描述方法和检查项。真实域名、主机、网络、部署/备份位置、运行镜像和连接资料由部署方私有保存，不属于源码文档。约束见 [AGENTS.md](../AGENTS.md)，技术差异见 [Fork 维护](fork-maintenance.md)。

## 版本与环境

1. 区分工作树、Git提交、发布包和运行镜像；使用完整提交或带哈希的源码快照构建，保留产物清单。
2. 本 Fork 的迁移36是金额方向，上游同号迁移在本 Fork 为37，多账号迁移为38并保留最低1分。以 `src/version.ts` 和实际迁移校验和判断兼容性，不能仅比较应用版本或 schema 数字。
3. 根 Compose 是上游通用安装模板。部署定制实例时将 `app`、`backup`、`maintenance` 的镜像统一固定到已验证的定制版本，不能默认使用上游 latest 覆盖现有库。
4. 公网采用HTTPS、正确的公开origin和可信直接代理；代理地址依据实际连接确认，避免使用任意来源。示例域名使用 `pay.example.com`。

构建包含服务端、管理端、收银台客户端及SSR产物；修改React源码不会自动更新运行镜像。前端增量发布也必须证明其后端/依赖/数据库没有对应变更。

## 发布顺序

- 先对比实际配置和运行文件，预构建镜像并进行隔离测试；测试不调用真实支付或通知目标。
- 等待安全窗口：核对OPEN/UNPAID收银台、正在查账及PENDING/LEASED/RETRY_WAIT通知。不能为抢占窗口取消客户订单。
- 按[维护流程](maintenance.md)停止相关进程并处理锁/租约；一致性备份数据库、主密钥和配置。先在副本验证迁移、完整性、外键及原业务数据保留。
- 同版更新应用、备份和维护工具，恢复原设置；核对 `/healthz`、`/readyz`、schema、权限、静态/SSR产物及回调配置。
- 保留发布记录和回退材料。真实付款、退款或人工关联不作为自动健康检查；需要单独授权。

`/healthz`表示进程/数据库健康，`/readyz`表示当时收款准入就绪，都不证明某笔付款已到账。生产截图、原始日志和财务数据不提交到公开仓库。

## 数据与回退

数据库、备份、主密钥分别保存；数据库备份不包含主密钥。以应用实际挂载的密钥目录/卷为准，不能把镜像VOLUME生成的同名匿名挂载当作真实主密钥副本。

运行中SQLite不只复制主文件；使用支持的一致性备份。迁移后旧镜像可能拒绝新库，本 Fork升级至38后不能直接切回只支持37或36的版本。已有新交易时不能通过恢复旧库覆盖新数据；先评估兼容修复或可验证恢复方案。

镜像保留当前及上一版，删除前检查容器与Compose引用；镜像清理不包括数据、密钥或备份卷。

## 私有交接记录应包含什么

| 信息 | 用途 |
| --- | --- |
| 核验日期、运行镜像、源码/产物哈希 | 识别真正运行版本 |
| 服务目录、Compose、端口及代理关系 | 安全定位和检查环境 |
| 数据、密钥和备份位置 | 迁移与恢复 |
| 探针、资源、未完成工作、验收范围 | 选择发布窗口，避免夸大验证 |
| 备份、回退兼容范围、恢复结果 | 应急处置 |

这些实际值在私有运维记录中填写。公开仓库只保留此结构；新会话缺少私有资料时先完成通用准备，通过安全渠道获取授权访问方式，不猜测生产环境。
